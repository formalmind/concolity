# Fuzzer benchmark: Async Swap's price book, forge against concolity

`concolity bench` on asyncswap/contracts at fead63f, run on 2026-10-26 on one Mac (all cores).

| Setting | Value |
|---|---|
| Mutated | `src/libraries/RadixPriceTree.sol`, `EligiblePrice.sol` and `TickPrice.sol`: 38 operator sites on lines the fuzz tests run; 30 run, spread evenly, all compiled |
| Harnesses | the 65 fuzz tests of 11 files (`test/RadixPriceTree.t.sol`, `test/EligiblePrice.t.sol`, and nine `test/formal/` files on the tree, the bit set and the tick key) |
| Budget | 2 s per fuzz test, in every tool |
| Kill | a test fails on the mutant, and the same input passes on the original (replayed on the unmutated bytecode) |
| Total time | 35 min |

## Kills

| Tool | Killed (of 30) | False kills | Only this tool | Median time to kill |
|---|---|---|---|---|
| forge (default) | 23 | 0 | 0 | 0.22 s |
| forge, coverage-guided | 0 | 0 | 0 | none: forge crashed on all 30 |
| concolity (z3 on every untaken side) | 22 | 0 | 0 | 0.27 s |
| concolity, solver off | 23 | 0 | 0 | 0.009 s |

- **Nothing is unique.** Every mutant one tool killed, another killed too. The three that ran found the same 23,
  except that concolity with the solver missed one.
- **The solver didn't pay here.** These mutants flip an equality or a comparison on a value the test computes. The
  first random or edge-value input catches them, so time spent solving delays the kill. `TickPrice.sol:17`
  (`!=` → `==`) shows it: forge killed it at 10.2 s, concolity with the solver off at 26 s, and concolity with the
  solver not within its budget. The solver had spent the time on other sides.
- **Time to kill is mostly test order.** forge's 0.22 s is its start-up: the first test it ran failed. Its 2.2 s
  kills are one test's full 2 s before the next one, and so are concolity's 12 to 13 s on `RadixPriceTree.sol:106`.
  The figures say which tool reached the killing test first. They say little about how fast each fuzzes one test.
  The next version should report each tool's time inside the test that killed the mutant.
- **forge's coverage-guided mode crashed on every mutant**: `fatal runtime error: stack overflow, aborting` after
  about 0.25 s. On the original it ran to its budget. Before the benchmark stopped runs that went too long, a single
  test file with `--fuzz-timeout 1` ran for 5 minutes, and 19 with `--fail-fast`, at 500 to 700% CPU, until it was
  killed. Coverage-guided mode stops working once a test fails. It is also the mode that reported
  a false failure on calldata solc's decoder rejects (HUNTING §3). Both need a minimal repro before an issue to
  foundry-rs.

## The seven survivors

No tool killed these. Each one is an equivalent mutant or a test gap.

| Mutant | Verdict from the code |
|---|---|
| `TickPrice.sol:29` `num / den >= 1 << 128` → `num * den >= 1 << 128` | **test gap**: every order whose amounts multiply past 2^128 (two 1e20 amounts) would get the end key. No fuzz test checks `key` on large amounts against the exact price |
| `TickPrice.sol:26` `num / den < 1 << 64` → `num * den` | likely a test gap: it changes which regime computes the square root. Each regime is within a tick, so only a test at tick boundaries with large amounts would see it |
| `TickPrice.sol:29` `>=` → `>` | equivalent: at exactly 2^128 the second regime's root is past `MAX_SQRT_PRICE`, so `MAX_TICK` either way |
| `TickPrice.sol:32` `<` → `<=` | equivalent: `getTickAtSqrtPrice(MIN_SQRT_PRICE)` is `MIN_TICK` |
| `EligiblePrice.sol:78` `==` → `!=`, `&&` → `\|\|` | equivalent in result: the condition only stops the walk up early. Changing it costs gas or does redundant writes, and the summaries stay the same |
| `RadixPriceTree.sol:54` `>` → `>=` | open: whether a branch on the insert path can have `bit == splitBit` |

## What to change

1. **Fuzz first, solve when coverage plateaus** (FUZZ.md §7). Running the solver from the first run spends the budget
   on sides random inputs would reach anyway.
2. **Per-test time to kill**, so test order stops deciding the comparison.
3. **Harder mutants**, where the solver should matter: equality guards on input values, and sequences (the invariant
   suites). This set mostly mutates comparisons on computed values, which random inputs kill in one run.
4. **A `TickPrice.key` property test** with large amounts against the exact cross-multiplied price. It would kill the
   two TickPrice survivors that are test gaps.
